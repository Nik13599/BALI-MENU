# BALI ID — служебные переводы от имени гостя (резерв, отключено)

## Текущий статус

**Служебный перевод от имени гостя не включён.** В `admin.html` и `director-id.html` зарезервирована форма с намеренно отключённой кнопкой и контрактом `bali-bonus-transfer-scaffold.js`. Этот модуль не отправляет запросы на списание или зачисление. Гостевой перевод уже реализован отдельно: кнопка «Перевести» на собственной BALI ID вызывает защищённую функцию `transferBaliBenefits`; подтверждённая операция отражается в историях обоих гостей. Оставшиеся разделы описывают резерв служебного интерфейса.

## Совместимость с существующим BALI ID

- Персональный номер — существующий `baliIds/{uid}.number`, уникальный и выдаваемый последовательно; нельзя создавать второй идентификатор.
- Уровни `Member / Silver / Gold / Platinum / Black / Private` независимы от накопленных бонусов и не передаются.
- Для будущих количественных бонусов использовать `guestWallets/{uid}` — именно такую коллекцию и модель `grants[]` предусматривает серверный PR #30; **не создавать параллельную `guestBonusWallets`**.
- Пример записи гранта (новое поле `transferable` по умолчанию `false`):

```json
{
  "id": "grant_...",
  "kind": "cocktail",
  "remaining": 3,
  "originalCount": 3,
  "unlimited": false,
  "transferable": false,
  "eventRef": null,
  "expiresAt": null,
  "issuedBy": "staffUid",
  "sourceTransferId": null
}
```

- Имена типов: `cocktail`, `shot`, `hookah`, `entry`. Свободный вход можно передавать лишь тогда, когда конкретный грант явно отмечен transferable. Процентные скидки, уровни статусов, безлимитные права, подарки с ограничением на событие и истёкшие бонусы **не переводятся**.

## Будущий запрос перевода

Только проверенные роли `director` или `admin`. Служебная форма передаёт номер карты отправителя, номер получателя, тип, количество, grantId (идентификатор конкретного бонусного начисления), неизменяемый idempotencyKey, но **не устанавливает клиентский баланс**.

Проверки сервера:
1. Проверить роль по защищённым `admins/{uid}` / `staffRoles/{uid}`, а не доверять клиентскому интерфейсу.
2. Разрешить только разные существующие BALI ID; разрешение на использование относится к конкретному `grantId`, имеет явный флаг `transferable:true`, положительный целый остаток и не истёкший срок.
3. Прочитать обе записи `guestWallets` внутри **одной Firestore transaction**. Для одновременных переводов/списаний использовать повтор транзакций.
4. Уменьшить у отправителя остаток на N, создать у получателя грант на N с **тем же сроком, eventRef, kind, условиями использования и provenance**; не восстанавливать истёкшие или потраченные права.
5. Создать `bonusTransfers/{transferId}` в той же транзакции (идентификаторы обоих UID и номеров карт, вид, количество, grantIds, staffUid, staffRole, createdAt, idempotencyKey, статус). Дополнительно создать ссылку в `walletOperations` или однотипный аудит из PR #30.
6. Не допускать double-spend: повтор запроса с одним idempotencyKey не выполняет перевод повторно. Корректировки только отдельной обратной операцией в аудите.

## Доступ и безопасность

`firestore.rules` включает:
- `guestWallets/{uid}`: чтение самим гостем, директором/администратором; **никаких клиентских изменений**.
- `bonusTransfers/{transferId}`: никакого прямого клиентского чтения/создания/редактирования/удаления.

Будущие записи и выдача истории должны проходить через серверную Firebase Callable Function с авторизацией и строгой пагинацией. Правила Firestore из репозитория **не публикуются автоматически GitHub Pages**. Без серверной интеграции оставлять флаг `TRANSFER_FEATURE.enabled=false` и отсутствие обработчика перевода.
