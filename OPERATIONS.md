# Эксплуатация BALI MENU

## Подключение нового режима хранения фото

Адаптивные фотографии галереи уже поставляются как статические ресурсы Hosting/CDN. Дополнительно реализован режим загрузки новых фото из админки в Firebase Storage. Для него требуется настроенный bucket; доступность и условия тарифа проверяются в Firebase Console владельцем проекта.

1. Убедитесь, что `storageBucket` в `firebase-config.js` совпадает с bucket проекта `bali-menu-5a48b`.
2. Разверните `storage.rules` через `firebase deploy --project bali-menu-5a48b --only storage`, используя учётную запись с правами на проект. При первом включении межсервисной проверки ролей Storage → Firestore Firebase может запросить разрешение сервисному агенту; проверьте его в Console.
3. Проверьте тестовым администратором загрузку, публичное открытие изображения, отказ гостю и отказ на файл больше 180000 байт. Автотесты эмулятора проверяют эти ограничения локально.
4. Только после проверки выставьте `window.BALI_IMAGE_STORAGE_ENABLED = true`. Код использует существующую Google-сессию и роль `admins/{uid}.active`, отдельные ключи в браузер не добавляются.

При включённом режиме сбой Storage явно останавливает загрузку: нет скрытого возврата к Base64 или публикации неверной ссылки. Подготовка WebP остаётся локальной. Повторный файл с тем же SHA-256 переиспользуется; URL сохраняется в существующем поле меню/афиши. Существующие ссылки и data URI продолжают читаться. Старые изображения автоматически не удаляются и не мигрируют: это сохраняет опубликованные материалы и позволяет отменить изменение режима. Массовую миграцию/очистку следует выполнять отдельной операцией после резервной копии и проверки ссылок.

## Мониторинг

- В обзоре админки раздел «Состояние подключения и диагностика» показывает здоровье текущего браузера. Экспорт ограничен 40 событиями и не сохраняет сообщения исключений, URL, токены, email, номера телефонов и данные заказов.
- Для серверных функций доступны структурированные записи `event="bali.callable"`: операция, исход, код ошибки и durationMs. Перед появлением этих записей нужно развернуть обновлённые функции существующим ручным backend workflow.
- В Logs Explorer рабочего проекта фильтруйте `jsonPayload.event="bali.callable"` и `jsonPayload.outcome="error"`; ошибки уровня ERROR отделены от ожидаемых отказов и ошибок ввода уровня WARNING. Для Cloud Run с другим способом представления console-записей используйте поиск `bali.callable` в textPayload.
- Централизованный сбор всех браузерных ошибок и облачные политики оповещений не настроены без доступа владельца. Локальная диагностика не является глобальной статистикой. Выбранный пользователем канал уведомлений — внутри сайта; внешние email/Telegram-сообщения не отправляются.

## Уведомления

Используются существующие авторизованные снимки заказов, дополнительных публичных коллекций с заказами нет. В LocalStorage сохраняются только курсоры `ID → последний статус`, максимум 100 записей на учётную запись. Лента сообщений хранится в памяти, очищается при смене аккаунта; курсоры предотвращают повторную выдачу уже замеченных статусов. При недоступном LocalStorage работает память текущей вкладки. Проверка повторов между вкладками выполняется через сохранённые курсоры, но это не гарантия exactly-once при строго одновременных обновлениях в разных вкладках. Уведомления служат подсказкой; список заказов остаётся источником состояния.

Первый снимок новой сессии без курсоров тихий: исторические заявки не объявляются новыми. При открытом сайте пустая начальная очередь всё равно уведомит о первом новом заказе. Сайт не использует Web Push и не сообщает об изменениях, пока браузер закрыт.

## Проверка в рабочем окружении

Эмулятор не заменяет проверку реального OAuth и развёрнутых правил. После предоставления доступа владельца используйте два специально выделенных Google-аккаунта и тестовое мероприятие:

1. Гость: вход → профиль → предзаказ → изменение → просмотр собственных заявок.
2. Сотрудник: вход → роль администратора → новый заказ → подтверждение → выполнен.
3. Гость: получить уведомление и убедиться, что подтверждённый заказ нельзя изменить.
4. Второй гость: запрет чтения чужого профиля, заказа, строк заказа и кошелька.
5. Отмена отдельного ожидающего предзаказа, недоступное блюдо, закрытая дата и повторная попытка отправки.
6. Визуальная проверка телефона, ПК, чайной карты и клавиатурного доступа.

Не добавляйте в репозиторий сервисные JSON-ключи или пароли пользователей. В этой работе рабочие заказы, роли, бонусы, расписание и составы блюд автоматически не переписывались.
