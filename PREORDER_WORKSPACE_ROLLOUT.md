# BALI: отдельная рабочая страница предзаказов

## Адреса
- `preorders.html` — самостоятельный рабочий интерфейс для сотрудников, только предзаказы.
- `admin.html` — общая админка; содержит переход на новую страницу и кнопку ручного создания.

## Возможности
- Заказы от гостей и по телефону в единой очереди, фильтры по дате и конкретному мероприятию.
- Ручное создание по имени, телефону (+код страны), столу или ID брони, блюдам кухни. Зарегистрированный аккаунт **не требуется**.
- Необязательное поле email для привязки к существующему аккаунту в `users`: если указано, заявка появится в «Моих заказах» этого гостя; привязка проверяется заново в Firestore-транзакции.
- Нумерация `EVENT №N` отдельная для каждого мероприятия, выдаётся транзакционно через `orderCounters`.
- Изменение статуса, редактирование даты/мероприятия/состава, отмена, архивация, печать, CSV с подробными заказами и сводкой блюд.
- «Удалить навсегда» запрашивает явное подтверждение и удаляет `orders/{id}` вместе с `items` одним batch. Поэтому запись пропадает в реальном времени у гостя и в общей очереди; локальные уведомления гостя также перестают показывать удалённый ID. Удаление необратимо.
- Кнопка ручной очистки всех заказов старше 30 дней. События, меню, карточки BALI ID и профили пользователей она не удаляет.

## Правила безопасности
- Все данные читаются и изменяются через Firebase Auth + `admins/{uid}.active=true`, дополнительно проверяются `firestore.rules`.
- `source:'staff'` и `createdByUid` допустимы только для заказов, созданных проверенным администратором.
- Для привязанных заказов Firestore Rules проверяют существование профиля и совпадение email.
- Гости не могут удалять заказы непосредственно. Номер заказа нельзя изменить без корректной транзакции счётчика.
- Отмена и архивирование **не означают удаление**.

## Срок хранения
- **Отсчёт 30 дней:** с момента `createdAt`, не с даты вечеринки.
- Обе интерфейсные истории перестают показывать записи старше 30 дней сразу при новом получении снимка; CSV тоже исключает их.
- Физическое автоматическое удаление на сервере реализовано функцией `expireBaliPreorderHistory`: ежедневно в 03:10 по Минску она выбирает записи старше 30 дней и выполняет `recursiveDelete` для родительского заказа и всех вложенных данных.
- Функция требует **развёртывания Cloud Functions и действующего Cloud Scheduler**. До её развёртывания физическая автоматическая очистка не включена; администратор может нажать «Удалить историю старше 30 дней». Код в GitHub сам по себе не запускает серверную задачу.
- Копии данных вне рабочей Firestore (резервные копии/скачанные CSV/логи) не удаляются действиями интерфейса.

## Выпуск и проверки
1. Проверить pull request и CI `BALI preorder workspace checks`. Он проверяет исходники, Firebase Emulator с правилами и изолированный UI smoke test.
2. Влить в `main`, дождаться опубликования HTML/JS/CSS GitHub Pages.
3. Опубликовать **новые** `firestore.rules` в проект `bali-menu-5a48b` (workflow на main запускается при изменениях rules). Пока правила не опубликованы, операции создания/удаления будут отклоняться.
4. После проверки состояния Firebase/Google Cloud и настройки авторизации развернуть `expireBaliPreorderHistory` из каталога `functions`. Нужен доступ к Cloud Scheduler и соответствующий тариф. Не запускать деплой, пока не проверены права сервисной учётной записи.
5. Протестировать на тестовом мероприятии: заказ без аккаунта, заказ с привязанным аккаунтом, изменение состава, CSV, отмену, «Удалить навсегда», отсутствие заказа у гостя и в админке; затем проверить очистку старых тестовых записей.
6. Счётчики `orderCounters` **не сбрасываются** при удалении истории, чтобы не создавать повторяющиеся номера в одном мероприятии.

> Не смешивать историю предзаказов с историей операций BALI ID и бонусов: они не затрагиваются этими кнопками.
