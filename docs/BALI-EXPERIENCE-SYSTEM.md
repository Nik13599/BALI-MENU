# BALI NIGHTCLUB — система пользовательского опыта и дизайн-качества

Версия: 20.10.2026 · Веб-сайт BALI-MENU · Минск, Кирова, 13  
Статус: рабочий стандарт для проекта, **не** результат интервью с гостями и **не** утверждённый брендбук.

## 1. Смысл перед оформлением

### Проверенные исходные данные

- Ночной клуб BALI: Минск, ул. Кирова, 13.
- Публичные вечеринки: пятница и суббота, 23:00–06:00.
- Вместимость: **500+ гостей**, есть три бара, собственная кухня, сцена, танцпол, оборудование света и звука, экраны и возможность адаптировать планировку.
- Сайт совмещает афишу, календарь, ознакомительные барную/кальянную/чайную карты, предзаказ кухни, профиль, BALI ID и административный интерфейс. Эти сценарии подтверждаются существующими файлами проекта.

### Группы пользователей — **гипотезы**, пока без интервью/аналитики

| Посетитель | Его вопрос на первом экране | Ожидаемое действие | Страница |
|---|---|---|---|
| Гость вечеринки | «Что происходит в ближайшие выходные?» | Смотреть календарь → афишу → отметить интерес | Главная → Календарь |
| Организатор мероприятия | «Подойдёт ли площадка под мой формат?» | Узнать факты, увидеть клуб на видео → позвонить/написать | Главная → О клубе → Контакты |
| Гость с предзаказом | «Что из еды можно заказать и когда?» | Выбрать блюда → корзина → авторизация → заказ | Меню кухни |
| Гость, изучающий ассортимент | «Что есть в баре/чайной/кальянной?» | Посмотреть карту и цены, без ложного CTA предзаказа | Бар/чай/кальян |
| Постоянный гость | «Какие у меня привилегии?» | Открыть личную BALI ID → QR / историю / перевод | Профиль → BALI ID |
| Сотрудник | «Что требует обработки сейчас?» | Очередь заявок → статус / подтверждение / печать | Админка |

**Неизвестно без данных:** доля мобильных посетителей, конверсия сайта, популярные форматы событий, реальные причины отказа от заявки. Не подставлять выдуманные проценты.

### Краткий анализ открытых сайтов в Минске (20.10.2026)

- [RICH HALL](https://www.richhall.by/): на первом экране сочетает формулировку ценности, **«Забронировать дату»**, описание форматов и площадки. Вывод для BALI: отделить гостя вечеринки от заказчика площадки, дать каждому свою кнопку.
- [BOGEMA](https://karaoke.by/): короткая эмоциональная презентация заведения и доступное действие бронирования. Вывод: BALI должен показывать фирменную атмосферу и путь к действию без перегруза.
- [Room Event Place](https://www.room.of.by/): показывает формат аренды, возможности, контакты и CTA. Вывод: преимущества BALI объяснять конкретными данными, а не абстрактными эпитетами.

Это **качественный анализ видимых страниц**, а не исследование продаж и не доказательство эффективности чужих конверсий. Не копировать чужую графику.

## 2. Первый экран и смысловые сценарии

Для каждого блока есть последовательность: **контекст → обещание → доказательство → действие**.

**Главная мобильная:** «BALI — больше, чем клуб» → «Площадка для мероприятий в центре Минска» → «Подробнее о клубе». Рядом — афиши реальных мероприятий. Не добавлять скрытые форматы и неподтверждённые скидки.

**Главная на ПК:** сохранить живой промоблок, календарь и BALI ID. В блоке «О клубе» разделить действия **«Площадка и аренда»** и **«Афиша вечеринок»**. Не прятать кнопки внутри декоративного оверлея.

**О клубе:** факты → видео о клубе (вместо фотогалереи) → форматы событий и контакты. Видео запускается по намеренному нажатию пользователя; есть ссылка на оригинал при недоступности встраивания. Не выдумывать содержание видео.

**Календарь:** дата → реально опубликованное событие → подробности и действие. Не придумывать даты афиш или «свободные места».

**Меню:** название, порция, цена и состав → действие. Предзаказ только кухни; на бар/кальян распространяется существующее подтверждение возраста и режим ознакомления.

**BALI ID:** имя, номер, статус, подтверждённые привилегии; переворот карты не мешает кнопкам «История», «Перевести» и QR.

## 3. Премиальная подача BALI (LIME SHADOW)

| Токен | Принцип |
|---|---|
| Фон | Тёмный графит и чёрный, не синий |
| Текст | Матовый белый для информации первого уровня; приглушённый светлый серый — для вторичного |
| Акцент | Лайм через установленный `--bt-primary`, **не** вводить второй конфликтующий акцент |
| Шрифты | Manrope — функциональный UI и тексты; Unbounded — ключевые заголовки |
| Кнопки | Компактные прямоугольники со скруглением, высокая читаемость, одна очевидная первичная кнопка |
| Карточки | Тонкая граница, сдержанная поверхность; тени и стекло — только по назначению |
| Логотип | Использовать существующий оригинальный asset, не пересоздавать |
| Навигация | Единое семейство фирменных пиктограмм ПК/телефон/ID |

Новые правила задаются в `bali-experience-system.css`; источником правды для цветов остаётся тема проекта, а не зашитый в отдельных страницах цвет. Не подменять фирменные изображения синтетическими.

## 4. Анимация и интерактив — функциональность выше эффектности

- Наведение карточки: деликатная смена рамки/смещение **только** на устройствах с hover и точным указателем.
- Горизонтальная карусель событий — горизонтальный жест; случайный вертикальный скролл не должен сломать статичный экран.
- BALI ID: сохранение существующего управления переворотом и 3D-представления без автоматического вращения.
- Видео: запуск по нажатию, полноэкранный режим, перезапуск, остановка при уходе из «О клубе».
- `prefers-reduced-motion: reduce`: отключение исключительно декоративных переходов; функции остаются рабочими.
- **Не делать:** автозапуск видео со звуком, тяжёлые 3D-библиотеки «ради красоты», автоматическое открытие модалок без намерения гостя.

## 5. Мобильная версия — самостоятельный сценарий

| Экран | Телефон | ПК |
|---|---|---|
| Главная | Вертикально компактный смысловой блок, события свайпом, фиксированная нижняя навигация | Горизонтальные функциональные зоны и постоянная боковая навигация |
| Меню | Один широкий невысокий товар в строке, понятные кнопки ± и корзина | Сетка карточек согласно существующим настройкам и категориям |
| Календарь | Читаемые дни, месяц и афиши без горизонтального переполнения окна | Календарь и афиши рядом |
| Профиль и ID | Статичный экран, модальные подробности с собственной прокруткой | Без случайного вертикального скролла, полноценная карта |
| О клубе | Видео 16:9, факты, затем действия | Видео и преимущества во всю доступную контентную область |

Контрольные размеры тестов: **320×640, 390×844, 1440×900**. Дополнительно вручную проверять планшет около 820px и узкий ноутбук около 1280px. Не скрывать важные действия при малой высоте.

## 6. Согласованность бренда на разных носителях

Интерфейс, BALI ID, обложки для афиш, Instagram и рекламные баннеры должны сохранять **одинаковый логотип, формы кнопок, типографические роли и характер акцентов**, но афиша события вправе иметь собственную цветовую тему. Не накладывать обязательный лаймовый фильтр на весь контент мероприятий.

Для публикации в соцсетях: единое расположение логотипа и даты, безопасные поля под интерфейс платформы, без «Листай дальше» по умолчанию. Реальные исходные афиши не перерисовывать автоматически и не выдумывать артистов, даты, цены.

**Управление из админки:** рядом с редактором главной добавлена сворачиваемая памятка. Её задача — помочь оператору проверить текст, актуальность данных и адаптивные кадры до сохранения.

## 7. Контроль качества и критерии принятия

### Автоматические проверки

1. Статический анализ и сборка стилей без случайной смены порядка каскада.
2. Экран «О клубе»: видео присутствует, 11 фото и галерея не создаются.
3. Переключение 4 карт меню: contextual copy соответствует активной карте. Не открывать бар/кальян без age gate.
4. Навигация по разделам: главная, календарь, меню, профиль, ID, инфо; правильные aria-атрибуты.
5. Блоки не переполняют ширину на проверяемых viewport; виден keyboard focus.
6. Возраст, предзаказы, история BALI ID и управление ролями остаются в существующих тестах.

### Ручная приёмка перед слиянием в main

- Проверить видео на опубликованном HTTPS-сайте: YouTube-встраивание зависит от внешней стороны.
- Проверить живые картинки из админки, не только локальные заглушки.
- Проверить реальную авторизацию, роли сотрудника, создание/изменение/отмену заказа, QR и перевод бонусов на тестовых аккаунтах в Firebase.
- Замерить Core Web Vitals на реальном мобильном интернете; без замеров **не** заявлять «быстрее на 40%».
- Убедиться, что экран BALI ID и главная остаются статичными, а каталог/диалоги скроллятся по назначению.

### Известные ограничения на дату работы

На базовой ветке CI уже обнаружены ошибки компиляции `firestore.rules`, несоответствия числа колонок и теста уведомлений. Новый дизайн **не** считается готовым к рабочему развёртыванию, пока эти ошибки не разобраны. Также не проводится самостоятельное исследование реальных пользователей — это отдельная задача с согласованным сбором данных.

## Принцип дальнейших доработок

**Не масштабировать CSS «слой на слой» бесконечно.** После утверждения визуального стандарта свести дублирующиеся правила в несколько компонентов и убрать ненужные `!important` при сохранении регрессионных тестов. UI-изменения проходят последовательность: смысл → прототип → мобильная композиция → desktop → доступность → проверка на работающих сценариях → публикация.
