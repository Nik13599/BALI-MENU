# BALI STAFF — отдельный доступ сотруднику

Страница: `https://baliminsk.by/preorders.html`.

## Подтверждённая текущая модель доступа
Рабочая страница BALI STAFF уже существует. Вход через Firebase Auth:
- личный Google-аккаунт сотрудника с подтверждённой почтой;
- альтернативно отдельный логин/пароль в Firebase Auth (когда режим Google Sheets выключен);
- владелец через Google.
Доступ к предзаказам в режиме Firestore определяется `admins/{uid}` или
`preorderStaff/{uid}`, а не кнопками страницы. В режиме Google Sheets
используется защищённая операция `me` на backend, возвращающая роль `staff`
или `admin`. **Назначить права в обоих backend требуется отдельно.**

## Как предоставить доступ одному сотруднику при действующем Firebase backend
1. Сотрудник входит через Google по ссылке BALI STAFF. До назначения роли
   система покажет отказ в доступе (это нормально).
2. В Firebase Console → Authentication → Users найдите запись сотрудника
   и скопируйте его UID; проверяйте совпадение email до выдачи прав.
3. В Firestore Database вручную создайте документ
   `preorderStaff/{точный-UID-сотрудника}` с полями:
   - `active`: boolean `true`;
   - `role`: string `preorders`;
   - `name`: string с именем сотрудника.
4. Повторно войдите на `preorders.html`.
5. Проверьте, что сотрудник видит предзаказы, но **не может** работать
   в `admin.html` и `director-id.html`.

### Отзыв доступа
Установите `active=false` в документе сотрудника. После этого
серверные проверки запретят новые разрешённые операции, но
уже открытый интерфейс может требовать обновления страницы.

## Если включена Google Sheets интеграция
Переключатель `BALI_GUEST_PREORDER_ENABLED` переводит staff UI в режим
`sheetsRequest("me")`. Firestore роль **не гарантирует** выдачу доступа
в Google Sheets режиме. Нужно назначить роль `staff` в используемом
backend по UID/email из проверенного Firebase ID token; не писать роль
в общедоступную таблицу и не доверять переданному клиентом email.
В текущей сессии реальное назначение конкретному сотруднику не выполнено:
его Google UID и рабочая серверная конфигурация не предоставлены.

## Принцип минимальных полномочий
Никогда не создавайте сотруднику запись в `admins` и не назначайте
`staffRoles.role=director` для доступа к предзаказам.
Не передавайте пароль владельца. Не используйте один аккаунт
на нескольких сотрудников. Действующий клиент не служит средством
присвоения ролей.


## Служебный вход без Google
На `preorders.html` форма логина/пароля остаётся видимой и при Google Sheets режиме.
Используется существующий Firebase Authentication Email/Password, но сотруднику
показывается только простой логин. Внутренний email строится как
`staff+<логин>@staff.baliminsk.by`. Этот адрес технический идентификатор,
**не рабочий почтовый ящик**; нельзя использовать его для восстановления пароля
без отдельного административного процесса.

Для реального входа владелец должен:
1. Включить Email/Password в Firebase Authentication → Sign-in method.
2. Создать сотрудника **через защищённый интерфейс владельца / Admin SDK** с
   техническим email, случайным сильным паролем и `emailVerified=true`
   только после ручной проверки владельцем. Не включать публичную саморегистрацию
   персонала; клиентскую кнопку регистрации не создавать.
3. Получить UID созданного пользователя и назначить ему минимальную роль
   `preorderStaff/{uid}` с `role="preorders"`, `active=true`,
   `name="<имя>"` в Firestore. Для режима Sheets дополнительно выдать
   роль `staff` на защищённом Sheets backend.
4. Проверить отказ для неверного пароля, неавторизованного UID, выключенной роли,
   а также запрет на директорскую и общую админ-панель.

Пароль не сохранять в Google Таблицах, репозитории, документации, логах
или браузерном localStorage. Не отправлять его через мессенджер в открытом виде.
